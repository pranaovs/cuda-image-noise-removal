============================================================================== 1. THE PREMISE IN ONE PAGE ==============================================================================

A digital photo picks up noise: some pixels come out of the camera (or the transmission channel) completely wrong. Our project removes that noise, using a method from a 2013 conference paper, and does it three times:

denoise_seq one CPU core, plain C -> the reference denoise_omp all CPU cores, OpenMP -> parallel CPU denoise_cuda the GPU, CUDA -> parallel GPU

The rule the whole project is built around:

THE PARALLEL VERSIONS MUST PRODUCE EXACTLY THE SAME BYTES AS THE
SEQUENTIAL REFERENCE.

Not “a similar image”. The same bytes. That is checked with cmp and with a maxdiff of 0 on every channel of every pixel. This constraint is why the code uses integer arithmetic everywhere it can, and it is the honest way to compare three implementations: if the outputs differ, a speed comparison is meaningless.

The second rule: every number is timed the same way in all three binaries, because all three share one main() (section 7). A speedup that came from timing different things would be worthless.

One-line summary for the professor:

"We reimplemented a fuzzy peer-group impulse-noise filter with an exact
 two-phase detect/filter split, made the OpenMP and CUDA versions
 bit-identical to the sequential one, and measured where the time actually
 goes -- it is FP64 arithmetic on the GPU, not memory traffic."

============================================================================== 2. IMAGES, FOR SOMEONE WHO HAS NEVER DONE IMAGE PROCESSING ==============================================================================

2.1 A pixel, and why 3 numbers

An image is a grid of pixels. Each pixel has three colour components: red, green, blue (RGB). Each component is one byte, range 0..255 (8 bits), where 0 = none of that colour, 255 = full.

1 pixel = 3 bytes = (R, G, B)
white  = (255, 255, 255)
black  = (0, 0, 0)
red    = (255, 0, 0)
grey   = (128, 128, 128)

A 1024 x 1024 image is therefore 1024 * 1024 * 3 = 3,145,728 bytes = 3 MB. Colour depth “24 bit” means 3 x 8 bit.

Why this matters for us: 8-bit integer pixels mean the arithmetic can be integer arithmetic, and integer arithmetic is exactly reproducible. A float sum can differ between CPU and GPU; an int sum cannot.

2.2 How the bytes are stored (this is the part that explains “layout”)

The image is one long row-major array: row 0 left to right, then row 1, etc. Pixel (x, y) starts at byte

offset = (y * width + x) * 3

That formula appears in the code as the inline function px() in src/common/image.h, and inline in the CUDA kernels. Two consequences:

  • Moving one pixel right is +3 bytes. Moving one pixel down is +3*width bytes.
  • A row is contiguous, so the GPU reads a row efficiently; a column is strided, so it is slower. All three implementations walk rows, not columns.

2.3 The file format: binary PPM (P6)

We use PPM because it needs no library. A P6 file is:

P6\n1024 1024\n255\n<then 3*w*h raw bytes>

That is: magic “P6”, width, height, max value 255, one whitespace, then the raw pixel bytes with no compression. image_read and image_write in src/common/image.c do exactly this, plus the “P3” ASCII fallback on read.

Why it matters: reading is trivial, so image I/O costs about a millisecond and is not part of the timed region (section 4.9 explains why that matters).

2.4 What “noise” means here

Two kinds of impulse noise:

Salt and pepper (what we use): a random density fraction of pixels is set to pure black (0,0,0) or pure white (255,255,255), all three channels at once. At density 0.10, 10% of pixels are destroyed.

Random-valued impulse noise: a random fraction of pixels gets a random value in 0..255. Harsher, because the damage is not at the extremes.

gennoise in src/common/noise.c implements both, driven by a seedable xorshift random generator, so the same seed gives the same noise on any machine. That is required for the three implementations to be compared on identical input.

How bad is 10% salt and pepper? PSNR of the noisy image against the clean one: 13.80 dB. For reference, 40 dB is “visually identical”, 30 dB is “good”, and below 20 dB the image is visibly destroyed. So 13.8 dB is very bad – which is the point: there is room to show a large improvement.

2.5 Why denoising is not just blurring

The obvious fix for noise is to average each pixel with its neighbours. That removes noise and also removes detail: edges get smeared, and after a while the image looks like it was shot through frosted glass.

The whole trick of the paper is: average only the neighbours that are NOT corrupted, and decide which ones are corrupted first, using local statistics. Edges survive because a neighbour on the other side of an edge does not look like the centre pixel, so it does not count as a peer and gets left out of the average.

That is the entire idea. Phase 1 decides who is corrupted, phase 2 averages only the clean ones.

2.6 The two quality metrics in the code

Both compare an output image against the clean original (src/common/metrics.c).

Mean absolute error (MAE), in units of “greyscale levels out of 255”:

MAE = (1/N) * sum over all bytes |a_i - b_i|        with N = 3*w*h

Peak signal-to-noise ratio (PSNR), in decibels:

MSE  = (1/N) * sum over all bytes (a_i - b_i)^2
PSNR = 10 * log10(255^2 / MSE)

PSNR is the standard image-quality number. It is logarithmic, so +10 dB is a 10x smaller squared error. Two warnings to have ready:

  • PSNR rewards blurring. A slightly blurred image can score higher than a sharp correct one. That is why we also report MAE and show a visual crop.
  • It is computed on the whole image, so a few bad pixels barely move it. That is why maxdiff exists: it is the maximum single-byte difference, and for us it must be 0.

maxdiff is in metrics_max_diff. It is the number that proves bit-identity.

============================================================================== 3. THE ALGORITHM, STEP BY STEP ==============================================================================

3.1 Terms

window a k x k square around a pixel; k = 3 by default, so 9 pixels. Set with -n. Must be odd, so there is a centre. Max 15. r radius, r = window / 2. For k = 3, r = 1. centre the pixel being decided. peer a window pixel that “looks like” the centre (definition below). d fuzzy tolerance, 0..1. Smaller = stricter = fewer pixels count as peers. Set with -d. Default 0.5. m peer cardinality threshold. A pixel is CLEAN if it has at least m+1 peers (itself included). Bigger m = stricter detection. Set with -m. Default 4.

Defaults came from measurement, not taste: the phase-06 sweep over d in 0.2..0.9 and m in 1..7 peaks at d = 0.5, m = 4 with 32.26 dB, and the peak is interior (0.4 and 0.6 are worse, m = 3 and m = 5 are worse).

3.2 The fuzzy distance (core.h:14)

For two pixels a and b, per channel:

t_c = 1 - |a_c - b_c| / 255           (1.0 if identical, 0.0 if 255 apart)

then combine the three channels multiplicatively:

dist = 1 - t_R * t_G * t_B

dist = 0 when the pixels are identical, and approaches 1 when they are maximally different. This is a fuzzy-set “similarity”, hence “fuzzy metric”. It is multiplicative rather than an average so that ONE badly different channel makes the pixels dissimilar – a red pixel is not 2/3 similar to a grey one.

It is also where all the time goes. Three channels, 9 window pixels, 3x3 window = 27 of these terms per pixel tested. That single fact explains the GPU result in section 9.

3.3 Phase 1 – detection (core.h:29, detectKernel)

For every pixel: count how many of its 9 window pixels (including itself) satisfy dist(centre, that) <= d if count >= m + 1 -> the pixel is CLEAN, mask = 0 else -> the pixel is CORRUPTED, mask = 1

Out-of-bounds coordinates (at the image border) are clamped to the nearest edge pixel, so a border pixel simply counts its edge neighbours twice. That avoids special cases and keeps every pixel comparable.

The mask is one byte per pixel, same dimensions as the image, written for every pixel. Nothing is parallel-unfriendly here: each pixel is decided from the input image only, never from the mask, so order does not matter.

At the shipped settings and 10% noise, roughly 1 in 10 pixels is flagged; that is measured, not assumed (see 3.5).

3.4 Phase 2 – repair (core.h:54, filterKernel)

For every pixel: if mask says CLEAN: copy the pixel through unchanged. if mask says CORRUPTED: average the pixels in the window whose mask is CLEAN, per channel, integer division: out_c = sum(clean neighbours_c) / count Note the centre is corrupted, so it is excluded automatically – it is a corrupted neighbour of itself. if there are NO clean pixels in the window (heavy noise), fall back to the per-channel median of the whole window.

Two properties to be able to defend:

  • The mean of only-clean-neighbours is what preserves edges: neighbours across an edge are usually a different colour, so they were flagged or at least are not the majority, and detail is not averaged away.
  • The median fallback is a safety net. It is rare: 8 pixels out of 71,301 corrupted at 10% noise (0.01%), 21,525 out of 367,839 at 50% (5.85%). We measured that with the fbcount tool, and the numbers are in results/quality_fallback.csv. That is why the fallback is not optimised: it almost never runs at the densities this filter is meant for.

3.5 Worked example, one pixel

Take a 3x3 window, all bytes 100 except one where a pepper pixel is 0, and the centre is the corrupted one:

100 100 100
100   0 100        centre = 0 (corrupted), the rest clean at 100
100 100 100

Detection for the centre: t_c = 1 - |0-100|/255 = 1 - 0.392 = 0.608 for each channel, so dist = 1 - 0.608^3 = 1 - 0.225 = 0.775. With d = 0.5, 0.775 > 0.5 so that neighbour is NOT a peer. Only the centre itself is a peer (distance 0), so count = 1. With m = 4 we need count >= 5, so 1 < 5 -> CORRUPTED. Correct.

Phase 2 for the centre, m = 4: 8 clean neighbours of value 100, no clean pixels? No – 8 of them are clean, so count = 8, sum = 800, out = 800/8 = 100 exactly. The 0 is gone and no blur was introduced.

Now the same computation for a clean pixel next to it: it has 8 peers around 100 and one at 0, count = 8 >= 5, so CLEAN, and phase 2 copies it through. Nothing changes in the clean part of the image. That is exactly what we want and it is what make check asserts on a clean photo (PSNR > 50 dB, measured 96.7 dB: a handful of extreme-edge pixels do fail the detector, and the sequential reference does exactly the same thing – it is the algorithm’s edge case, not a parallel bug).

3.6 Why the output is bit-identical across implementations

  • Every pixel is decided independently in phase 1 and written independently in phase 2: no atomics, no reductions, no accumulation order.
  • Phase 2’s mean is an integer sum divided by an integer count. Integer division truncates the same way on every machine.
  • The only cross-pixel dependency is the mask itself: phase 2 reads its neighbours’ mask bytes. Hence the hard rule below.

THE PHASE BARRIER is the single most important structural fact of this project:

Every pixel of phase 2 reads mask bytes of its neighbours.
Therefore the ENTIRE mask must be finished before ANY phase-2 pixel runs.

Sequential: the first loop ends, that is the barrier. OpenMP: two separate parallel for regions, each ends with an implicit barrier. CUDA: two separate kernel launches, because a launch is the only global barrier CUDA has. __syncthreads() only orders threads inside one block, so it cannot help – a neighbouring pixel may live in a different block.

Being able to say that sentence, and pointing at the two kernel launches in host.cu:87 and host.cu:89, is most of the GPU part of the exam.

============================================================================== 4. HPC CONCEPTS FROM ZERO ==============================================================================

4.1 Serial vs parallel

Serial: one instruction stream, one thing at a time. Parallel: several instruction streams working at once.

Three flavours matter for this course:

  • Shared memory multicore (OpenMP): one CPU, several cores, all see the same RAM. Threads are cheap to start; a race condition is the danger.
  • Accelerator (CUDA): a separate device with its own memory. The CPU (host) orchestrates and copies data over PCIe; the GPU (device) runs thousands of small threads with no shared cache coherence with the CPU.
  • Distributed memory (MPI, not used here): separate machines, message passing.

Our project uses the first two. Everything below is on the course’s list.

4.2 Time, throughput, speedup, efficiency

T(N) wall-clock time with N workers. Wall-clock is what the user feels. throughput pixels / time. We report Mpix/s = pixels / (ms * 1000). speedup S(N) = T(1) / T(N). How many times faster than one worker. efficiency E(N) = S(N) / N. Fraction of the ideal linear gain, 0..1.

Real numbers from results/bench.csv (10% noise, 1024 x 1024, median of 5): seq 39.67 ms -> 26.4 Mpix/s omp 4 threads 10.98 ms -> S = 3.61, E = 0.90 omp 20 threads 5.65 ms -> S = 7.02, E = 0.35 cuda 9.08 ms -> S = 4.37 against ONE cpu thread

Efficiency of 0.90 at 4 threads is the good result of the project: 90% of the ideal. Efficiency at 20 threads is 0.35, and section 9 explains precisely why.

4.3 Amdahl’s law, and why it is less interesting here than it looks

S(N) = 1 / ( s + (1 - s)/N )        s = serial fraction of the work

If 5% of the work cannot be parallelised, the best possible speedup is 1/0.05 = 20x no matter how many cores you buy. That is the standard exam answer for “what limits your speedup”.

In our project the serial fraction is small and mostly OUTSIDE the timed region: PPM parsing, writing the output, the noise generation and process start-up all happen outside the t0 ... t1 bracket in main_denoise.c:105. Inside it, the serial parts are the phase barrier (a loop exit, nanoseconds) and, for CUDA, the PCIe copies (7.8% at 4096^2).

So: say Amdahl, then say “it is not what limits us; our limits are hardware level – core heterogeneity and FP64 rate”. That is the stronger answer.

4.4 Strong scaling vs weak scaling

Strong scaling: keep the problem FIXED, add workers. Time should fall. This is section 4.2. Its limit is Amdahl + hardware. Weak scaling: keep the WORK PER WORKER fixed, add workers and grow the problem. Ideal is: time stays CONSTANT.

Weak scaling tests the machinery, not the algorithm. Ours (results/05 section 3): 1 thread on 1024^2 = 41.4 ms, 4 threads on 2048^2 = 42.9 ms. 4x the work, 4x the threads, +3.6% time. That is a clean pass and it is the check that says “we are not silently re-serialising as the image grows”.

4.5 Latency vs bandwidth

Latency: how long ONE operation takes (e.g. read 1 byte: ~400 cycles to DRAM). Bandwidth: how many bytes per second in total (e.g. 164 GB/s measured on the GPU for a read sweep).

Latency is hidden by parallelism; bandwidth is not. A GPU hides latency by having thousands of threads in flight; when the bandwidth is used up, more threads do not help. This distinction is what “memory-bound” means.

4.6 Memory hierarchy, and cache

Registers -> L1/shared (per SM, ~100 KB) -> L2 (shared by the GPU, MBs) -> DRAM (GBs). Each level is roughly 10x bigger and 10x slower than the one above.

A stencil like ours reads each pixel about 9 times (once per window position). If those 9 reads hit cache, the extra traffic is free; if they miss, you pay 9x DRAM traffic. That is the standard motivation for “tiling” (loading a block into shared memory once, then reading it 9 times from shared memory).

Our project measured it and it did NOT help: +0.2% at 4096^2. Keep this in your head as the honest answer to “did you try optimizing the memory access pattern?” – yes, and it was not the bottleneck. Section 9 gives the proof.

4.7 Memory-bound vs compute-bound. Arithmetic intensity.

arithmetic intensity = FLOPs performed / bytes moved

Low intensity (few flops per byte) -> memory-bound: adding cores does not help, the bus is already saturated. High intensity -> compute-bound: flops are the limit.

The usual assumption for a 3x3 stencil is “memory-bound, so tile it”. We measured the opposite for the GPU: 114.7 ms of kernel for 3.15 MB read + written, which is 0.027 GB in 0.115 s = 240 MB/s. The GPU can do 164 GB/s. So it is using 0.15% of the bandwidth: it is emphatically NOT memory-bound. It is bound by double precision arithmetic (4.8).

This is the highest-value paragraph in these notes. It is the project’s finding.

4.8 FLOPs, FP32, FP64 – the number that explains everything

A floating point number in 32 bits is “single precision” (float). In 64 bits it is “double precision” (double). Doubles have ~15 correct digits, floats ~7. Doubles cost more silicon and more time.

On a desktop/server CPU, FP64 runs at about half the FP32 rate, so nobody notices. On a consumer GPU, FP64 is deliberately crippled: the RTX 4050 does FP64 at 1/64 of its FP32 rate. It is a gaming/consumer part, and games do not use doubles.

Our code uses double for the fuzzy distance (core.h:14), because that is what the reference implementation did and because bit-identical output across CPU and GPU matters more than speed. Measured consequence, on this GPU:

detection kernel only, `double`      116.1 ms   (at 4096^2)
the same kernel in `float`             4.83 ms   -> 24x faster
integer |delta| arithmetic, no divide  0.819 ms  -> 142x faster
peak 1 - x/255 rate: double 84.9 G/s vs float 6003 G/s  = 70.7x

That is the whole story of the GPU numbers. The paper we reproduce says it uses “single-precision calculations”; we kept double for the bit-identity gate and report single precision as the untried lever. Being able to say “we knowingly paid 24x on the GPU to keep the bit-exact comparison, and here is the measurement that prices it” is a much better answer than pretending the code is optimal.

Also related: -use_fast_math is deliberately NOT enabled for the CUDA build (comment in src/cuda/CMakeLists.txt). It changes floating point rounding, which would break agreement with the CPU. Named, not used – that is a decision you can defend.

4.9 Why the timed region is placed where it is

main_denoise.c brackets only the call to the denoiser: t0 = now; DENOISE_FN(…); dt = now - t0;

So PPM reading, the clean-image clone, and writing are not counted. Reasons: - I/O is serial and would flatten every speedup curve (Amdahl in the wrong place). - All three binaries share this main(), so the bracket is identical for all three. A speedup cannot be a measurement artefact, it can only be code. - -r N repeats the call N times and reports the BEST time, after all allocations warmed up. Reported as “median of 5 outer runs, best of 3 inner reps” in the CSVs.

4.10 Reproducibility: why we insist on byte-identity

Floating point addition is not associative: (a+b)+c != a+(b+c) in general. So a parallel sum can legitimately differ from a serial sum. If a project claims “parallel is 8x faster” while producing a slightly different image, the claim is weaker: an optimiser could trade correctness for speed and nobody would see it.

By forcing integer arithmetic in phase 2 and fixing the summation order (each pixel’s mean is computed by exactly one thread, in window order, no reduction), we remove that escape hatch. maxdiff = 0 is then a real gate, checked by make check and by compute-sanitizer runs.

4.11 SIMD vs SIMT, and warps

SIMD: one instruction, several data lanes, all lanes do the SAME operation (SSE/AVX on the CPU). SIMT: one instruction, many threads, in groups of 32 called WARPS on NVIDIA hardware. All 32 threads in a warp execute the same instruction, but they may diverge: if 5 threads take the if branch and 27 the else, the warp runs both paths with the other lanes masked off.

Consequences used in this project: - Block sizes are multiples of 32 so blocks divide into whole warps. We use 16x16 = 256 threads = 8 warps. - Divergence is cheap in our kernel: phase 2’s if (!mask[i]) splits a warp into “copy 3 bytes” and “do the window loop”, but the copy path is trivial, so the wasted lanes cost almost nothing. In phase 1 every thread does the same work, so there is no divergence at all.

4.12 Occupancy

Occupancy = active warps per SM / the maximum the SM supports. It is limited by registers per thread, shared memory per block and threads per block. More occupancy = more latency hiding.

Ours: 256 threads per block, no shared memory, so occupancy is set by the thread limit per SM (2048 / 256 = 8 blocks resident). With no profiler installed on the box (ncu and nsys are absent), this is arithmetic, not a measured counter – say that honestly if asked. The API that WOULD measure it, cudaOccupancyMaxActiveBlocksPerMultiprocessor, is on the course scope sheet.

4.13 PCIe: the GPU’s extra tax

The GPU has its own memory. Data must be copied host -> device before the kernel and device -> host after it. That copy goes over PCIe at a measured ~11 GB/s each way on this laptop.

Measured split (median, 4096^2): 4.61 ms H2D + 114.65 ms kernel + 5.06 ms D2H. So the transfer is 7.8% of the call. At 512^2 it is 10.5%, and at ~256^2 it would dominate and the GPU would LOSE to the CPU. This is the standard “GPU is not always faster” answer, with our own numbers.

That is also why h2d/kernel/d2h are reported as three separate numbers and never summed into the kernel claim: charging PCIe to “GPU compute” would make the speedup look worse than the kernel really is, and it would be dishonest.

============================================================================== 5. CUDA FROM ZERO ==============================================================================

5.1 Vocabulary

host the CPU and its memory device the GPU and its memory kernel a function that runs on the GPU, declared global device a helper function callable only from GPU code thread one lane of execution; we use one thread per pixel block a group of threads that can share memory and synchronise grid all the blocks of one launch threadIdx, built-in variables giving a thread’s position inside its block, blockIdx, its block’s position inside the grid, and the block/grid sizes blockDim, gridDim SM streaming multiprocessor – the GPU’s core cluster; the 4050 has 20 of them stream a queue of work; the default stream runs in order, which is what we rely on

5.2 The launch syntax, and how a thread finds its pixel

dim3 block(16, 16);                    // 256 threads per block
dim3 grid((w + 15) / 16, (h + 15) / 16);
detectKernel<<<grid, block>>>(args);

Inside the kernel:

int x = blockIdx.x * blockDim.x + threadIdx.x;
int y = blockIdx.y * blockDim.y + threadIdx.y;
if (x >= w || y >= h) return;                        // the guard
mask[y * w + x] = ...;

Read that as: block 3 covers x = 48..63 in row 0..15, and thread (5,2) inside it handles pixel (53, 2). The grid is rounded UP so that images whose width is not a multiple of 16 are still fully covered; the extra threads in the last block fall off the edge and hit the guard. The 1001x333 test image exists precisely to make that path run (1001 = 62*16 + 9).

5.3 The four steps of a CUDA program (lecture 2)

1. cudaMalloc   allocate device buffers
2. cudaMemcpy   host -> device (H2D)
3. kernel<<<>>> launch
4. cudaMemcpy   device -> host (D2H)

host.cu:63 denoise_cuda is exactly these four, plus timing. Three device buffers: input image, output image, mask (w*h bytes). They are allocated once and kept in statics (host.cu:45 buffers_reserve) because a cudaMalloc of ~100 MB costs more than the kernels and would pollute the reported time.

Note what does NOT happen: the mask is never copied back to the host. No host code reads it, and a D2H copy of w*h bytes would inflate d2h_ms with data nobody looks at. That is a deliberate, defensible omission – and the reason the function takes a mask argument it does not use, with (void)mask; and a comment saying why.

5.4 Asynchrony, and why cudaEvent timing exists

A kernel launch is ASYNCHRONOUS: <<<>>> returns immediately, the CPU continues, and the GPU runs the kernel later. So you cannot time a kernel with clock_gettime on the CPU: you would be timing the launch, not the work.

cudaEventRecord(ev0);                        // timestamp on the GPU's queue
cudaMemcpy(...);        cudaEventRecord(ev1);
detect<<<...>>>;  filter<<<...>>>;  cudaEventRecord(ev2);
cudaMemcpy(...);        cudaEventRecord(ev3);
cudaEventSynchronize(ev3);
cudaEventElapsedTime(&ms, ev1, ev2);         // kernel time, on GPU clocks

That is host.cu:78-107. Four events = three intervals = H2D, kernel, D2H. This is the correct way to time GPU work and it is worth one sentence in the exam.

5.5 Why two kernels and not one

Because of the phase barrier (3.6). One kernel cannot read other blocks’ mask bytes reliably: there is no cross-block synchronisation inside a launch, and __syncthreads() only syncs a single block. The launch boundary on the default stream IS a full barrier.

Alternatives that exist and why we did not use them: a grid-wide barrier needs cooperative launch (banned by the course scope sheet), or a two-pass “read mask into shared” trick that cannot see other blocks.

5.6 Errors: check every call

#define CUDA_CHECK(call) do { cudaError_t e_ = (call); \
    if (e_ != cudaSuccess) { fprintf(stderr, ...); exit(1); } } while (0)

Every API call is wrapped. After each launch we call cudaGetLastError() because a launch can fail for reasons the compiler cannot see (bad grid size, too much shared memory requested, invalid device pointer); without that check a broken kernel is silently a no-op and you debug the wrong thing for an hour.

And beyond the checks: compute-sanitizer (NVIDIA’s valgrind-for-CUDA) reported 0 errors on 1024^2, 4096^2, the 1001x333 guard path and window 15, including initcheck (which proves no thread reads memory that was never written – i.e. the launch boundary really does provide the barrier).

5.7 What the course scope sheet bans, and what we use

Banned and unused: __ldg, __restrict__, kernel templates, vector types (uchar3/float4), dynamic shared memory, texture memory, cooperative groups, CUDA graphs, dynamic parallelism, CUB/CUTLASS, tensor cores, __launch_bounds__, maxrregcount, half2.

Used: __global__, __device__, threadIdx/blockIdx/blockDim/gridDim, __syncthreads (not needed, mentioned), atomics (not needed), basic runtime API, cudaEvents, fixed grid sizes, block multiple of 32 <= 1024, CUDA_CHECK around every call, cudaGetLastError after every launch.

One caveat to be ready for: dim3 is not on the sheet’s list, but a 2-D grid needs it, and 2-D launch is the taught “going 2-D” form. Say that if it comes up.

What we dropped on purpose after measuring: a shared-memory tiled variant. It was written, verified bit-identical, and gave +0.2%. It was deleted rather than shipped, because it doubled the code for no measurable gain. That story is results/04 section 4.

============================================================================== 6. OPENMP FROM ZERO ==============================================================================

6.1 What it is

A set of compiler pragmas that turn a plain loop into a multithreaded loop. No library calls, no thread management: you annotate, and the compiler generates thread creation, work distribution and the join.

Model: FORK-JOIN. The program starts with one thread. At #pragma omp parallel for, a team of threads is forked, the loop iterations are split, and at the end of the region they join back into one thread.

6.2 The two pragmas in this project (src/omp/denoise_omp.c:17 and :24)

#pragma omp parallel for collapse(2) schedule(static)
for (int y = 0; y < h; y++)
    for (int x = 0; x < w; x++) ...

parallel for split the iterations among threads collapse(2) flatten the two loops into one iteration space of h*w, so the split is over pixels, not over rows. Without it, only rows are distributed – fine for 1024 rows, terrible for 8 rows. schedule(static) give each thread one contiguous chunk up front, no runtime bookkeeping. Right choice when every iteration costs the same, which is true here: a 3x3 window per pixel, always.

6.3 Implicit barriers, or “why there is no race condition”

Each parallel for region ends with an implicit barrier: all threads wait, then continue. Two separate regions therefore give the phase barrier for free (3.6).

Within a region, is there a race? No: - Phase 1: thread for pixel (x,y) reads only the INPUT image (never written) and writes mask[y*w+x]. One writer per address. No race by construction. - Phase 2: writes out[y*w+x], reads the input image and the (finished) mask. One writer per address again. - No reductions, no critical, no atomics, no reduction(+:sum) anywhere. A pure data-parallel map: pixel in, pixel out.

“Each output element is written by exactly one thread and depends only on read-only or already-finished data” is the sentence that proves correctness.

6.4 static vs dynamic scheduling

static: split into N equal chunks before the loop starts. No synchronisation overhead. Bad if iterations cost wildly different amounts (one thread finishes early and idles).

dynamic: hand out one chunk at a time from a shared counter; a fast thread takes more work. Costs an atomic per chunk but balances the load.

We use static because our work is uniform. Reportable consequence: on this machine static was actually a liability, because the cores are NOT uniform (section 9.2) – a static equal share hands the same pixels to a slow E-core. That is a genuinely interesting measured result and worth saying out loud: “the textbook argument for static holds only if the cores are identical; ours are not, and we measured 15.19 ms with explicit static split versus 10.84 ms with the default placement”.

6.5 The environment variables (and why a benchmark must set them)

OMP_NUM_THREADS=N how many threads OMP_PROC_BIND=close pin threads to the nearest available cores (stops the OS migrating them mid-loop) OMP_PLACES=cores define “one place” as one core, so binding is per core

Without pinning, the OS may move a thread to another core between iterations, which destroys cache locality and makes timings wobble by tens of percent. Every benchmark and every check in this repo exports these three.

6.6 Physical vs logical cores, P-cores vs E-cores, SMT

Modern Intel laptop CPUs are hybrid: fast P-cores (performance, with hyperthreading = SMT, 2 logical threads per physical core) and slow E-cores (efficiency, no SMT, no hyperthreading, roughly 1/3 of the speed for this kind of work).

This machine: i7-13700H = 6 P-cores + 8 E-cores = 14 physical cores, with the 6 P-cores giving 12 logical CPUs, total 20 logical CPUs.

Consequences we measured, at 1024^2: 6 threads on the 6 P-cores 7.33 ms (5.4x) 12 threads on the 6 P-cores with SMT 7.09 ms (SMT buys ~nothing) 8 threads on the 8 E-cores 20.13 ms (an E-core is ~2.9x slower) 20 threads, everything 4.60 ms (8.6x)

So “more threads” is not monotonic on a hybrid CPU, and a demo of OMP_NUM_THREADS=14 doing worse than 4 threads is not a bug in the code. Section 9.2 has the full explanation.

6.7 What OpenMP does not give you

No vectorisation guarantee, no GPU offload in this project, no distributed memory, and no protection against data races – the programmer still has to know that the parallel loop’s iterations are independent. collapse(2) does not make them independent; it only flattens them.

7.1 There is no hand-written Makefile

7.3 The trick that makes the comparison fair: DENOISE_FN

All three denoisers are compiled from THE SAME src/app/main_denoise.c. Only one macro differs:

                                            DENOISE_HAS_CUDA=1)

  • argument parsing (-d/-m/-n/-r/-q), the repetition loop, the timing bracket and the report line are identical, byte for byte, in all three binaries;
  • a speedup cannot come from one binary timing something the other does not;
  • adding an implementation costs 3 lines of CMake and one function.

This is the single best design decision in the repo to point at. It is why the numbers in results/bench.csv are comparable at all.

8.1 core.h is the algorithm. Everything else is scheduling.

This is the sentence to open with when the professor points at the code. core.h has no threads, no GPU, no OpenMP, no I/O: three pure functions that define the semantics. denoise_seq, denoise_omp and both CUDA kernels are transcriptions of those three functions with different scheduling. If they ever disagree, the bug is in the transcription, and maxdiff != 0 says so immediately.

8.2 What happens when you run denoise_cuda, step by step

  1. main_denoise.c: read the noisy PPM into src, parse -d/-m/-n/-r/-q, allocate the mask (w*h bytes on the host).
  2. For each of reps (default 5): clone the noisy image, t0 = now, call denoise_cuda_impl (via DENOISE_FN), dt = now - t0, keep the best.
  3. host.cu:63 denoise_cuda:
    1. create 4 cudaEvents (first call only)
    2. buffers_reserve: cudaMalloc in/out/mask, reused on later calls
    3. event 0, cudaMemcpy H2D, event 1 <- h2d_ms
    4. detectKernel<<<grid,block>>> + cudaGetLastError
    5. filterKernel<<<grid,block>>> + cudaGetLastError
    6. event 2 <- kernel_ms
    7. cudaMemcpy D2H, event 3, synchronise <- d2h_ms
    8. store h2d/kernel/d2h into g_last
  4. kernels.cu: each thread computes its (x,y), returns if outside, and does either detection (writes 1 mask byte) or repair (writes 3 bytes).
  5. back in main: write the PPM, compute psnr/mae if -q was given, print one line: impl=cuda threads=1 ms=… mpix_s=… h2d_ms=… kernel_ms=… d2h_ms=… psnr=… mae=…

The one thing that does NOT happen: the mask never comes back to the host. The host mask buffer from step 1 is unused in the CUDA path ((void)mask;).

8.3 The buffer swap (denoise_seq.c:28)

Phase 2 cannot write into the image it is reading, because a neighbouring pixel must read the ORIGINAL value, not one already repaired. So it writes into a second buffer and swaps the pointers at the end – no 3 MB memcpy. Same in CUDA: g_in is read-only during the kernels, g_out is written. Aliasing in/out would still be “correct-ish” in phase 2 for clean pixels but would corrupt corrupted neighbours, so the two-buffer design is required, not stylistic.

8.4 kernels.cuh: keeping CUDA out of the C build

main_denoise.c is plain C. It cannot see __global__, cudaEvent_t or any CUDA type. kernels.cuh therefore declares only C-compatible things: two functions and a CudaTiming struct of three doubles, inside extern "C". The __global__ prototypes live in host.cu, the only other file that needs them (host.cu:18-21).

That is why the CUDA split (h2d/kernel/d2h) can be printed by the shared main without #include <cuda_runtime.h> anywhere in the C code. If asked “how do the CPU and GPU parts talk”, this header is the answer.

============================================================================== 9. THE THREE FINDINGS ==============================================================================

The project has three results worth defending. Everything else is engineering.

9.1 Byte-identical parallelism is achievable, and it is the strong claim

seq, omp and cuda produce the same bytes: maxdiff = 0 on 512^2, 1024^2, 2048^2, 4096^2, on window 5 and 15, on the odd 1001x333 size, and on repetitions. PSNR agrees to 4 decimals: 32.2613 for all three.

Why it works: one thread per pixel, one writer per address, integer arithmetic in phase 2, and a real global barrier between the phases.

Why it matters: a speedup claim next to a changed image is weak. Ours is not.

9.2 The OpenMP curve is non-monotonic, and the cause is measured

At 1024^2 (median of 5): 1T 41.4, 2T 21.4, 4T 11.0, 8T 11.9, 14T 13.6, 20T 5.65 ms.

Two things are wrong with the naive story: - 8 threads is SLOWER than 4. - 14 threads (all physical cores!) is 2.4x slower than 20 threads (with SMT).

Cause, measured by pinning threads explicitly: - OMP_PLACES=cores on a hybrid CPU does not mean “one place per physical core”. libgomp enumerates in Linux CPU order: 14 places = 12 P-core siblings + 2 E-cores. Six E-cores are never used, and the 12 P-threads contend for 6 physical cores. - With schedule(static) and 14 equal chunks, each E-core gets the same pixel count as a P-core and takes ~2.9x longer. The wall time is set by the slowest chunk. - With 20 threads, each chunk is smaller, so the E-core chunks are smaller too, and the wall time drops to 4.6 ms.

Numbers: 6 P-cores alone 7.33 ms, 12 with SMT 7.09 ms (SMT adds nothing), 8 E-cores alone 20.13 ms, 14 explicit P+E split 15.19 ms, 20 threads 4.60 ms.

Exam sentence: “The plateau at physical core count is not a property of our code; it is a property of a hybrid CPU plus static scheduling. The fix in production would be schedule(dynamic) or chunks proportional to core speed. We measured the placement effect instead of guessing it.”

9.3 The GPU is FP64-bound, not memory-bound – proven, not assumed

The plan was the textbook move: a 3x3 stencil reads each pixel 9 times, so load tiles into shared memory and cut the traffic. It was implemented, verified bit-identical, and measured: +0.4% at 1024^2, +0.2% at 4096^2. Nothing.

Proof by probe (4096^2, same block shape, same clamping, three throwaway variants): detection only, double 116.1 ms detection only, float 4.83 ms (24x) detection only, integer 0.819 ms (142x) same at 1024^2: kernel 8.34 ms, of which detection is nearly all of it measured DRAM read bandwidth: 164 GB/s the kernel actually uses ~240 MB/s = 0.15% of it peak rate of 1 - x/255: double 84.9 G/s vs float 6003 G/s = 70.7x

So: 27 fuzzy terms per pixel, each a double divide, on a consumer GPU whose FP64 rate is 1/64 of FP32. The memory system is idle. Adding shared memory cannot help arithmetic.

Consequence for the report: the GPU is 4.4x (1024^2) to 5.2x (4096^2) faster than ONE cpu thread, but LOSES to 20 OpenMP threads at 4096^2 (124 vs 76 ms). Not because the GPU is bad, because the workload is double precision on a 70 W laptop part with crippled FP64. Changing double to float is the lever, and that is what the paper did.

9.4 (bonus) The default parameters came from a sweep, not from taste

7 values of d x 7 values of m = 49 configurations on photo_1024 at 10% noise. Peak: d = 0.5, m = 4 -> 32.26 dB, MAE 0.91. Interior maximum in both directions. That is why params_default is 0.5/4 and not the paper’s 0.6/2.

Before the sweep the defaults gave 25.20 dB; after, 32.26 dB. Same code, +7 dB from two constants. Worth mentioning: it is the cheapest quality win in the project and it required no parallel code at all.

============================================================================== 10. THE PAPER, AND WHAT WE DID DIFFERENTLY ==============================================================================

Citation: Sanchez, Vidal, Bataller, Arnal, “A Parallel Method for Impulsive Image Noise Removal on Hybrid CPU/GPU Systems”, ICCS 2013, Procedia Computer Science 18:2504-2507 (4 pages, a short paper).

What it proposes: - impulsive (salt & pepper / random-valued) noise removal, - the “peer group” idea: a pixel is clean if enough of its neighbours are similar to it under a fuzzy metric, - two phases: detect the corrupted pixels, then filter only those, - implemented twice: OpenMP on the CPU, CUDA on the GPU (“hybrid”), with speedups reported against the sequential version, - SINGLE PRECISION calculations.

What we took from it: the peer-group / fuzzy-metric algorithm and the two-phase structure. That is section 3.

What we did differently, and why: 1. DOUBLE precision, to get bit-identical output against the CPU reference. Cost, measured: the GPU is ~24x slower than it would be in float. Benefit: a maxdiff = 0 gate instead of “looks similar”. This is the main engineering trade and it is a deliberate, priced decision. 2. We did NOT reproduce its memory optimizations, because they do not pay on this hardware (9.3) – and the course scope sheet bans most of them anyway. 3. We measured the serial fraction instead of assuming Amdahl explains everything, and found hardware limits instead (core heterogeneity, FP64). 4. We re-tuned d and m by sweep rather than reusing the paper’s values.

What to say if asked “did you reproduce the paper?”: “We reproduced the algorithm and the two-phase decomposition, and we reproduced the qualitative CPU/GPU result – both are much faster than sequential. We did not reproduce its numerical result, because we kept double precision where the paper uses single, so our GPU numbers are far below what theirs would be on this hardware. We quantified that gap instead of hiding it: 24x.”

That is an honest and specific answer, which is what examiners reward.

============================================================================== 12. TWENTY QUESTIONS WITH SHORT ANSWERS ==============================================================================

Q1. What does the program do? Removes salt & pepper / impulse noise from a PPM image using a fuzzy peer-group detector, in three implementations that produce identical bytes.

Q2. Why three implementations? To separate “the algorithm” from “the scheduling”: same semantics, three ways to distribute the pixels. It is the course’s core activity.

Q3. Why must the outputs be identical? Because otherwise a speedup could be bought by changing the result. Integer arithmetic + one writer per pixel makes identity achievable, and maxdiff = 0 is then a real test. Verified with cmp and compute-sanitizer.

Q4. Why two phases and not one loop? Phase 2 reads its neighbours’ MASK bytes, so the whole mask must be complete first. That is a global barrier; a single fused kernel cannot have one.

Q5. How do you get a global barrier in CUDA? A kernel launch. __syncthreads() only synchronises one block. Grid-wide barriers need cooperative launch, which the course scope bans.

Q6. Why is the grid rounded up? width/height need not be multiples of 16 (test case 1001x333); the last block overshoots and those threads hit if (x >= w || y >= h) return;.

Q7. Why 16x16 blocks? A 2-D mapping matches the 2-D image and is the taught form; 256 is a multiple of 32 so it splits into 8 whole warps; it is well under the 1024 limit; and it is fixed so the result is reproducible.

Q8. Why is timing done with cudaEvent, not clock_gettime? A launch is asynchronous; the CPU clock would time the launch, not the work. Events are recorded in the GPU’s stream and measure real device time.

Q9. Why separate H2D / kernel / D2H? They are different costs with different causes: PCIe vs compute. Summed together, a slow copy would be blamed on the kernel. Ours: 4.6 / 114.7 / 5.1 ms at 4096^2.

Q10. Did you use shared memory? Why not? A tiled variant was written and measured: +0.2%. The kernel is FP64-bound; the DRAM bandwidth is 99.85% idle. Deleted rather than shipped.

Q11. Why double precision if it costs 24x? To be bit-identical to the CPU reference. It is a deliberate trade, priced by measurement, and single precision is named as the next lever (the paper uses single).

Q12. What limits the OpenMP speedup? Not Amdahl; core heterogeneity. 6 P-cores are ~3x faster than the 8 E-cores, OMP_PLACES=cores gives odd placement on a hybrid part, and static scheduling makes slow cores set the wall time. Measured: 6P 7.33 ms, 8E 20.13 ms, 20 threads 4.60 ms at 1024^2.

Q13. Is there a race condition in the OpenMP loops? No. Each output element is written by exactly one thread and reads only read-only data (input image) or data guarded by a barrier (mask). No reductions, no atomics.

Q14. What does collapse(2) do? Flattens the (y, x) loop nest into a single space of h*w iterations, so threads are distributed over pixels instead of over rows.

Q15. Static vs dynamic schedule? Static: equal chunks, no overhead, right when every iteration costs the same. Dynamic: pull work from a counter, balances unequal work. Ours is uniform, so static is right in theory – and it is exactly what hurt on unequal cores, which is the measured finding.

Q16. How do you know the CUDA code is correct and not just lucky? maxdiff = 0 vs the sequential reference on 4 sizes, 2 windows, an odd size and repeats; compute-sanitizer memcheck and initcheck: 0 errors; make check gates it.

Q17. Why is the mask never copied back to the host? No host code reads it. Copying w*h bytes back would inflate D2H with data nobody looks at. The function still takes the argument for signature uniformity, with (void)mask; and a comment.

Q18. What is the serial fraction, and what does Amdahl predict? Inside the timed region: the phase barrier (negligible) and PCIe (7.8% for CUDA). The serial I/O is outside the timed region on purpose. Amdahl predicts a very high ceiling, which is why the real limits we found are hardware, not algorithmic.

Q19. Why is throughput flat across image sizes? The work per pixel is constant and there is no reuse of a working set, so time is linear in pixels. seq stays at ~26 Mpix/s from 512^2 to 4096^2.

Q20. What would you do with one more week? (a) implement the filter in single precision as an opt-in flag and measure the real speedup against a documented precision budget; (b) run a profiler (ncu/nsys are not installed on the box) to confirm the FP64 claim with counters instead of probes; (c) schedule(dynamic) for the hybrid CPU. Answer (a) first – it is the measured 24x lever.

What it does - Image is three fields: width, height, and one flat array of bytes. - px(img, x, y) returns a pointer to the first byte of that pixel: offset = (y * w + x) * 3. Border pixels therefore reuse their edge neighbours instead of needing special cases in the algorithm.

What to say if he points at it “One struct, flat byte array, row-major, no padding. The GPU reads this exact array, so there is no layout conversion and no risk of the CPU and GPU disagreeing about where a pixel lives. px() is the address arithmetic, and img_clamp() is the border policy.”

#ifndef CORE_H
#define CORE_H

#include <string.h>

#include "image.h"
#include "params.h"

/* The algorithm, no parallelism. Both denoise_*_impl and the CUDA kernels obey
 * exactly these semantics; only the scheduling differs. */

/* Bounded fuzzy distance: 1 - prod_c (1 - |a_c-b_c|/255).
 * identical -> 0.0, maximally different -> 1.0. */
static inline double fuzzy_dist(const unsigned char a[3], const unsigned char b[3])
{
    double prod = 1.0;
    for (int c = 0; c < 3; c++) {
        int d = (int)a[c] - (int)b[c];
        if (d < 0)
            d = -d;
        prod *= 1.0 - (double)d / 255.0;
    }
    return 1.0 - prod;
}

/* Phase 1: is the centre pixel clean? Counts window pixels within d of the centre
 * (the centre always counts itself) and demands count >= m+1. Out-of-bounds
 * coordinates clamp to the edge. */
static inline int is_clean(const Image *img, int x, int y, const DenoiseParams *p)
{
    int r = p->window / 2;
    int count = 0;
    const unsigned char *c = px(img, x, y);
    for (int dy = -r; dy <= r; dy++) {
        int yy = img_clamp(y + dy, img->h);
        for (int dx = -r; dx <= r; dx++) {
            int xx = img_clamp(x + dx, img->w);
            if (fuzzy_dist(c, px(img, xx, yy)) <= p->d)
                count++;
        }
    }
    return count >= p->m + 1;
}

static inline int cmp_u8(const void *a, const void *b)
{
    return (int)*(const unsigned char *)a - (int)*(const unsigned char *)b;
}

/* Phase 2: repair one corrupted pixel. Mean of the clean neighbours only (the
 * centre is corrupted, so it is excluded too). If no neighbour is clean, fall
 * back to the per-channel median of the whole window. Integer arithmetic only,
 * so every implementation produces identical bytes. */
static inline void repair_pixel(const Image *img, const unsigned char *mask, int x, int y,
                                const DenoiseParams *p, unsigned char *dst)
{
    int r = p->window / 2;
    int sum[3] = {0, 0, 0};
    int count = 0;

    for (int dy = -r; dy <= r; dy++) {
        int yy = img_clamp(y + dy, img->h);
        for (int dx = -r; dx <= r; dx++) {
            int xx = img_clamp(x + dx, img->w);
            if (mask[(size_t)yy * (size_t)img->w + (size_t)xx])
                continue;
            const unsigned char *q = px(img, xx, yy);
            sum[0] += q[0];
            sum[1] += q[1];
            sum[2] += q[2];
            count++;
        }
    }

    if (count > 0) {
        dst[0] = (unsigned char)(sum[0] / count);
        dst[1] = (unsigned char)(sum[1] / count);
        dst[2] = (unsigned char)(sum[2] / count);
        return;
    }

    unsigned char vals[PARAMS_MAX_WINDOW * PARAMS_MAX_WINDOW];
    for (int c = 0; c < 3; c++) {
        int n = 0;
        for (int dy = -r; dy <= r; dy++) {
            int yy = img_clamp(y + dy, img->h);
            for (int dx = -r; dx <= r; dx++) {
                int xx = img_clamp(x + dx, img->w);
                vals[n++] = px(img, xx, yy)[c];
            }
        }
        qsort(vals, (size_t)n, 1, cmp_u8);
        dst[c] = vals[n / 2];
    }
}

#endif

What it does, function by function

fuzzy_dist(a, b) Loops over the 3 channels. d is the absolute channel difference (0..255). 1.0 - d/255.0 is 1.0 for identical and 0.0 for opposite. The three are multiplied, then the result is subtracted from 1, so identical pixels -> 0.0 maximally different -> 1.0 Multiplication (not averaging) means one badly wrong channel is enough to make two pixels dissimilar. Loops = 3 divisions, and each is double.

is_clean(img, x, y, p) r = window/2 (1 for a 3x3 window). Two nested loops from -r to +r = the 9 window pixels. Coordinates go through img_clamp, so borders reuse edge pixels. Count how many window pixels have fuzzy_dist(centre, that) <= d. The centre itself is included and always counts (distance to itself is 0). Clean if count >= m + 1. Returns 1 (clean) or 0.

repair_pixel(img, mask, x, y, p, dst) Skips every window pixel whose mask byte is 1 (corrupted) – including the centre, which is corrupted by definition here. Sums R, G, B separately as INTEGERS and divides by the clean count. Integer division truncates, and truncation is identical on every CPU and GPU, which is half of why we get bit-identical output. The if (count > 0) guard handles the heavy-noise case. When it fires, the fallback copies the whole window into a stack array, qsort()s it, and takes the middle element per channel (the median). The comment says why there are no floats at all on this path either.

What to say if he points at it “This file is the specification. It has no threads, no pragmas, no CUDA: three functions that define exactly what the answer is. The three implementations are transcriptions of it with different scheduling, which is why a transcription mistake shows up immediately as maxdiff != 0. The only floating point is the fuzzy distance; the output arithmetic is integer, and that is what makes byte-identical results possible.”

Follow-up he may ask: “why is the distance not a difference of squares?” Because the paper defines a fuzzy similarity: per-channel membership (1 - |delta|/255) combined by product. It is ‘fuzzy’ in the fuzzy-set sense: each channel has a degree of membership in the set ‘similar to the centre’.

15.4 denoise_seq.c – the reference (31 lines, full) 
#include "core.h"

/* Sequential reference: two loops, one implicit barrier between them (the end of
 * the first loop). Phase 2 cannot read a partial mask, which is the only reason
 * the phases are not fused. */
void denoise_seq_impl(Image *img, unsigned char *mask, const DenoiseParams *p)
{
    const int w = img->w, h = img->h;

    for (int y = 0; y < h; y++)
        for (int x = 0; x < w; x++)
            mask[(size_t)y * (size_t)w + (size_t)x] = is_clean(img, x, y, p) ? 0 : 1;

    Image *out = image_alloc(w, h);
    for (int y = 0; y < h; y++) {
        for (int x = 0; x < w; x++) {
            size_t i = (size_t)y * (size_t)w + (size_t)x;
            unsigned char *dst = px(out, x, y);
            if (mask[i])
                repair_pixel(img, mask, x, y, p, dst);
            else
                memcpy(dst, px(img, x, y), 3);
        }
    }

    /* swap buffers instead of copying the whole image back */
    unsigned char *tmp = img->rgb;
    img->rgb = out->rgb;
    out->rgb = tmp;
    image_free(out);
}

What it does - Loop 1 writes one mask byte per pixel: 0 = clean, 1 = corrupted. - The end of loop 1 is the phase barrier, for free. - Loop 2 writes into a NEW buffer out. It must: a neighbour being read must still be the original noisy value, not an already-repaired one. Writing in place would corrupt the neighbourhood. - if (mask[i]) – corrupted: repair. Else: copy 3 bytes through. - At the end the two pointers are swapped, so the caller’s Image now owns the result. No 3 MB memcpy.

What to say if he points at it “Two passes with a buffer swap. The separate output buffer is required by the algorithm, not by style: phase 2 reads neighbours, so it cannot write over them. And the phase split exists because phase 2 reads the mask of its neighbours, so the whole mask must exist first.”

15.5 denoise_omp.c – parallel CPU (41 lines, full) 
#include "core.h"

/* OpenMP version: identical body to denoise_seq_impl, only the scheduling differs.
 * Two separate `parallel for` regions, so the phase boundary is a visible implicit
 * barrier: phase 2 reads its neighbours' mask, so the whole mask must be written
 * before any pixel is repaired. No reduction, no atomics, no critical section -
 * every pixel is written by exactly one thread.
 *
 * schedule(static) is right here because the work per iteration is uniform (a
 * fixed-size window per pixel), so a static block partition has no load imbalance
 * to chase and keeps each thread on the same rows (cache/walk locality). dynamic
 * would only add scheduling overhead. */
void denoise_omp_impl(Image *img, unsigned char *mask, const DenoiseParams *p)
{
    const int w = img->w, h = img->h;

#pragma omp parallel for collapse(2) schedule(static)
    for (int y = 0; y < h; y++)
        for (int x = 0; x < w; x++)
            mask[(size_t)y * (size_t)w + (size_t)x] = is_clean(img, x, y, p) ? 0 : 1;
    /* implicit barrier here: the mask is complete before phase 2 starts */

    Image *out = image_alloc(w, h);
#pragma omp parallel for collapse(2) schedule(static)
    for (int y = 0; y < h; y++) {
        for (int x = 0; x < w; x++) {
            size_t i = (size_t)y * (size_t)w + (size_t)x;
            unsigned char *dst = px(out, x, y);
            if (mask[i])
                repair_pixel(img, mask, x, y, p, dst);
            else
                memcpy(dst, px(img, x, y), 3);
        }
    }

    /* swap buffers instead of copying the whole image back */
    unsigned char *tmp = img->rgb;
    img->rgb = out->rgb;
    out->rgb = tmp;
    image_free(out);
}

What it does – and the only difference from the sequential file is 2 lines - #pragma omp parallel for: this loop’s iterations are shared among the thread team. - collapse(2): merge the y and x loops into one iteration space of h*w, so threads split pixels rather than rows. (Without it, 1024 rows over 20 threads is fine, but 8 rows over 20 threads leaves 12 idle.) - schedule(static): equal contiguous chunks, decided up front, zero runtime overhead. Justified because every pixel costs the same. - The end of each parallel for is an implicit barrier -> the phase barrier. - No reduction, no atomic, no critical, no #pragma omp single: nothing to synchronise, because each iteration writes a different byte.

What to say if he points at it “Same body as the sequential one, two pragmas. The barrier between phases is implicit at the end of the first parallel for – which is exactly the dependency we need, since phase 2 reads its neighbours’ mask. There is no race: one writer per output byte, and the reads are either read-only input or mask bytes protected by that barrier. static scheduling is the textbook choice for uniform work – and on this hybrid CPU it was measurably the wrong choice, which we report instead of hiding.”

Note the honest caveat to hold in reserve schedule(static) assumes identical cores. This CPU has 6 fast P-cores and 8 slow E-cores, so an equal split gives a slow core the same pixel count as a fast one and the wall time is set by the slowest chunk. Measured: 14 threads with an explicit 6P+8E split = 15.19 ms, versus 4.60 ms with 20 threads. If he pushes on “why static”, that measurement is the answer, plus “dynamic or speed-proportional chunks would be the production fix”.

/* The denoiser on the GPU: two kernels, one thread per pixel, plain global loads.
 * ... (scope comment: no shared memory, no templates, no vector types, no __ldg,
 *      no __restrict__, no dynamic parallelism) */
#include <cuda_runtime.h>

#include "kernels.cuh"

/* Keep a coordinate inside the image by replicating the edge, like core.h does. */
__device__ int dev_clamp(int v, int hi)
{
    return v < 0 ? 0 : (v >= hi ? hi - 1 : v);
}

/* One channel of the fuzzy metric: identical channels -> 1.0, 255 apart -> 0.0.
 * The distance is 1 - (product over the three channels). */
__device__ double dev_chan_term(int a, int b)
{
    int d = a - b;
    if (d < 0)
        d = -d;
    return 1.0 - (double)d / 255.0;
}

/* Phase 1 for one pixel: count how many window pixels are within d of the centre,
 * the centre included, and call it clean when there are at least m + 1 of them. */
__device__ int dev_is_clean(const unsigned char *in, int w, int h, int x, int y, DenoiseParams p)
{
    int r = p.window / 2;
    int count = 0;
    const unsigned char *c = in + 3 * ((size_t)y * (size_t)w + (size_t)x);
    for (int dy = -r; dy <= r; dy++) {
        int yy = dev_clamp(y + dy, h);
        for (int dx = -r; dx <= r; dx++) {
            int xx = dev_clamp(x + dx, w);
            const unsigned char *q = in + 3 * ((size_t)yy * (size_t)w + (size_t)xx);
            double dist = 1.0 - dev_chan_term(c[0], q[0]) * dev_chan_term(c[1], q[1]) *
                                    dev_chan_term(c[2], q[2]);
            if (dist <= p.d)
                count++;
        }
    }
    return count >= p.m + 1;
}

/* Insertion sort, used only by the rare median fallback (n <= 225). */
__device__ void dev_sort_u8(unsigned char *v, int n)
{
    for (int i = 1; i < n; i++) {
        unsigned char key = v[i];
        int j = i - 1;
        while (j >= 0 && v[j] > key) {
            v[j + 1] = v[j];
            j--;
        }
        v[j + 1] = key;
    }
}

/* Kernel 1 - detection. Writes the mask: 1 = corrupted, 0 = clean. */
__global__ void detectKernel(const unsigned char *in, unsigned char *mask, int w, int h,
                             DenoiseParams p)
{
    int x = blockIdx.x * blockDim.x + threadIdx.x;
    int y = blockIdx.y * blockDim.y + threadIdx.y;
    if (x >= w || y >= h)
        return; /* grid is rounded up, so the last block can hang over the edge */
    mask[(size_t)y * (size_t)w + (size_t)x] = dev_is_clean(in, w, h, x, y, p) ? 0 : 1;
}

/* Kernel 2 - filtering. ... */
__global__ void filterKernel(const unsigned char *in, const unsigned char *mask,
                             unsigned char *out, int w, int h, DenoiseParams p)
{
    int x = blockIdx.x * blockDim.x + threadIdx.x;
    int y = blockIdx.y * blockDim.y + threadIdx.y;
    if (x >= w || y >= h)
        return;

    const int r = p.window / 2;
    size_t i = (size_t)y * (size_t)w + (size_t)x;
    if (!mask[i]) {
        out[3 * i + 0] = in[3 * i + 0];
        out[3 * i + 1] = in[3 * i + 1];
        out[3 * i + 2] = in[3 * i + 2];
        return;
    }

    int sum[3] = {0, 0, 0};
    int count = 0;
    for (int dy = -r; dy <= r; dy++) {
        int yy = dev_clamp(y + dy, h);
        for (int dx = -r; dx <= r; dx++) {
            int xx = dev_clamp(x + dx, w);
            size_t j = (size_t)yy * (size_t)w + (size_t)xx;
            if (mask[j])
                continue; /* a corrupted neighbour must not pull the average */
            sum[0] += (int)in[3 * j + 0];
            sum[1] += (int)in[3 * j + 1];
            sum[2] += (int)in[3 * j + 2];
            count++;
        }
    }

    if (count > 0) {
        out[3 * i + 0] = (unsigned char)(sum[0] / count);
        out[3 * i + 1] = (unsigned char)(sum[1] / count);
        out[3 * i + 2] = (unsigned char)(sum[2] / count);
        return;
    }

    unsigned char vals[PARAMS_MAX_WINDOW * PARAMS_MAX_WINDOW];
    for (int c = 0; c < 3; c++) {
        int n = 0;
        for (int dy = -r; dy <= r; dy++) {
            int yy = dev_clamp(y + dy, h);
            for (int dx = -r; dx <= r; dx++) {
                int xx = dev_clamp(x + dx, w);
                vals[n++] = in[3 * ((size_t)yy * (size_t)w + (size_t)xx) + c];
            }
        }
        dev_sort_u8(vals, n);
        out[3 * i + c] = vals[n / 2];
    }
}

What it does, in the order a thread runs it

  1. int x = blockIdx.x * blockDim.x + threadIdx.x; Every thread works out which pixel it owns. blockIdx = which block, blockDim = block size, threadIdx = position inside the block. Because the block is 16x16 and the image is 2-D, this is a two-dimensional index; that is the whole reason for a 2-D grid.
  2. if (x >= w || y >= h) return; The guard. The grid is rounded up (see 15.7), so the last row/column of blocks can stick out of the image. Those threads must do nothing – not read, not write. Without this line the kernel would read past the buffer and compute nonsense.
  3. mask[...] = dev_is_clean(...) ? 0 : 1; phase 1, one byte out. or if (!mask[i]) { copy 3 bytes; return; } phase 2’s fast path: most pixels are clean, they cost 3 loads and 3 stores and no window loop at all.
  4. Phase 2’s slow path mirrors repair_pixel exactly: skip corrupted neighbours, integer sums, integer divide.
  5. The fallback: same window, sorted with an insertion sort written by hand because qsort does not exist on the device. n <= 225, so insertion sort is fine, and it only runs when nothing in the window is clean (0.01% of corrupted pixels at 10% noise).

Note on __device__ vs __global__ __device__ = callable only from GPU code, runs per thread, no launch. __global__ = a kernel: launched from the host with <<<grid, block>>>, runs once per thread, must return void. Everything shared between them is passed by value (w, h, and the params struct) because the device cannot dereference a host pointer.

What to say if he points at it “One thread per pixel, two kernels, plain global loads. The mapping from threadIdx/blockIdx to pixel is those first two lines, and the guard is what makes non-multiple-of-16 images safe. dev_chan_term is the same fuzzy term as core.h – the file is a transcription on purpose, so any drift shows up as maxdiff != 0 immediately.”

void denoise_cuda(Image *img, unsigned char *mask, const DenoiseParams *p, CudaTiming *t)
{

    const size_t nbytes = (size_t)w * (size_t)h * 3;
    (void)mask; /* the host mask is not needed: no D2H copy, see the end of this function */

    if (!g_ev_ready) {
        for (int i = 0; i < 4; i++)
            CUDA_CHECK(cudaEventCreate(&g_ev[i]));
        g_ev_ready = 1;
    }
    buffers_reserve(nbytes, (size_t)w * (size_t)h);

    /* 256 threads per block (16x16, a multiple of 32); grid rounded up so w and h need
     * not be multiples of 16. Overshooting threads bounce off the guard in the kernel. */

    CUDA_CHECK(cudaEventRecord(g_ev[0]));
    CUDA_CHECK(cudaMemcpy(g_in, img->rgb, nbytes, cudaMemcpyHostToDevice));
    CUDA_CHECK(cudaEventRecord(g_ev[1]));

    /* Two launches on the default stream. The second one cannot start before the first
     * has finished, and that ordering is the phase barrier the algorithm needs. */
    detectKernel<<<grid, block>>>(g_in, g_mask, w, h, *p);
    CUDA_CHECK(cudaGetLastError());

    CUDA_CHECK(cudaGetLastError());

    CUDA_CHECK(cudaMemcpy(img->rgb, g_out, nbytes, cudaMemcpyDeviceToHost));
    CUDA_CHECK(cudaEventRecord(g_ev[3]));
    CUDA_CHECK(cudaEventSynchronize(g_ev[3]));

    float h2d = 0.0f, kern = 0.0f, d2h = 0.0f;

cudaMemcpy(img->rgb, g_out, nbytes, D2H); device -> host
cudaEventElapsedTime(&kern, ev1, ev2);   kernel time, measured on the GPU
  • (w + 15) / 16 is integer ceiling division: 1001 -> (1016)/16 = 63 blocks, covering 1008 columns for a 1001-wide image. The 7 extra columns hit the guard. With 1000-wide input you would need this; without it you lose pixels.
  • The grid is 2-D and so is the block, so one launch covers the whole image.
  • buffers_reserve keeps the device allocations between repetitions. A cudaMalloc of 48 MB costs more than 100 ms of kernel, so allocating per call would corrupt the measurement.
  • Three intervals from four events: [0,1] = H2D, [1,2] = both kernels, [2,3] = D2H. Reported separately, never summed into “GPU time”.
  • g_last / denoise_cuda_last_timing exist because the shared main() is plain C and must not include a CUDA header just to print the split.

What to say if he points at it “The four CUDA steps from the lecture: allocate, copy in, launch, copy out. Two launches, because a launch is the phase barrier. Timing is cudaEvent pairs, because a launch is asynchronous so a CPU clock would measure the launch and not the work. And the transfers are reported separately from the kernel – 4.6 / 114.7 / 5.1 ms at 4096^2 – because charging PCIe to GPU compute would be wrong.”

15.11 The measurement helpers (short but exam-relevant)

Salt and pepper noise (src/common/noise.c, add_impulse_noise):

    for (size_t i = 0; i < n; i++) {
        unsigned char *p = img->rgb + i * 3;
        if (rng_double(&rng) >= density)
            continue;
        if (mode == NOISE_RANDOM_VALUED) {
            p[0] = (unsigned char)rng_below(&rng, 256);
            p[1] = (unsigned char)rng_below(&rng, 256);
            p[2] = (unsigned char)rng_below(&rng, 256);
        } else {
            unsigned char v = rng_below(&rng, 2) ? 255 : 0;
            p[0] = p[1] = p[2] = v;
        }
    }

Per pixel, roll a uniform number; if it is below density, destroy the pixel. Salt & pepper sets all three channels to 0 or 255 (a coin flip). The RNG is a seeded xorshift: same seed -> same noise on any machine, so all three implementations see identical input – which is what makes a byte comparison meaningful.

Metrics (src/common/metrics.c):

double metrics_psnr(const Image *a, const Image *b)
{
    size_t n = (size_t)a->w * (size_t)a->h * 3;
    double sse = 0.0;
    for (size_t i = 0; i < n; i++) {
        double d = (double)a->rgb[i] - (double)b->rgb[i];
        sse += d * d;
    }
    if (sse == 0.0)
        return INFINITY;
    return 10.0 * log10((255.0 * 255.0) / (sse / (double)n));
}

MSE over every byte (3wh of them), then PSNR = 10 log10(255^2 / MSE). Identical images return infinity, which is why the clean-image test asserts “> 50 dB” rather than “== infinity”. metrics_max_diff is the other half: the largest single-byte difference, which must be 0. metrics_identical is a memcmp. Those two are the correctness gate; PSNR is only the quality number.

fbcount (src/tools/fallback_count.c) counts corrupted pixels whose entire window is corrupted – i.e. how often the median fallback in core.h actually fires: 8 pixels out of 71,301 at 10% noise (0.01%), 21,525 out of 367,839 at 50% (5.85%). That is the measurement behind the claim “the fallback is rare, which is why it is not optimised”.
